# AI Threat Modeling App — Product Spec (v1)

Source methodology: *Enterprise AI Security — Threat Modeling Methodology & Architecture Assessment Appendices* (Part I stages 1–9, Appendices A–H).

## 1. Decisions

| Topic | Decision |
|---|---|
| Users | Single user. No accounts or backend. |
| Platform | Browser-only web app: React + TypeScript + React Flow. Runs fully client-side; can be hosted statically (e.g. GitHub Pages) or opened locally. |
| Persistence | Autosave to browser storage, plus **Save / Open assessment file (JSON)**. |
| AI assist | **No LLM in v1.** "Describe your system" uses rule-based keyword and phrase matching behind a `DescriptionAnalyzer` interface, so an LLM can be added later. |
| v1 scope | Stages 1–6: intake → architecture discovery → diagram → security objectives → threats → risk rating → treatments and patterns. Evidence tracker (App. G), sign-off (App. H) and reassessment triggers are deferred. |
| Diagram | Editable canvas with **two-way sync** to the model and questionnaire. One canvas with toggleable layers. |
| Threat frameworks | Appendix C domains, tagged with the latest **OWASP** lists (AI and traditional), **MITRE ATLAS**, **MITRE ATT&CK** and **STRIDE**. See section 4a. |
| Traditional security | **Built in everywhere**, not a separate module. Every component carries conventional AppSec, cloud and infrastructure questions and threat rules alongside its AI-specific ones. |
| Content editing | Question bank, component catalog, threat rules, patterns, framework mappings and the description lexicon are **all editable inside the app** (Settings → Libraries). |
| Report branding | None required. A plain, clean report. |
| Question depth | **Tiered by risk** (Light / Standard / Deep) from intake answers. The user can always expand. |
| Risk rating | Section 9 matrix by default; **configurable** in Settings to match the organization's approved matrix. |
| Starting points | Blank, starter template, or free-text description. |
| Exports | Report (PDF and Word/.docx). JSON assessment file. |

## 2. Core workflow (screens)

1. **Start** — choose one of:
   - Blank.
   - A template: RAG knowledge assistant, Agent with tools, Embedded/third-party AI, Traditional ML prediction service, or AI platform/gateway.
   - "Describe your system".
2. **Intake (Stage 1 / Appendix A)** — purpose, owner, system type, lifecycle stage, users and exposure, criticality, data classification, autonomy, deployment, dependencies, operations.
   - These answers compute the **assurance tier** and the **impact profile**.
3. **Architecture (Stage 2 / Appendix B)** — split view:
   - Left: **component palette**, grouped by the Section 7 categories (Actors, Entry points, Processing, Data, Capabilities, Effects).
   - Center: **canvas**.
   - Right: **property panel** for the selected node, edge or boundary, showing that component's Appendix B questions filtered by tier.
   - Each answer is **Yes / No / N/A / Unknown**, with a note, evidence, owner and due date. An Unknown becomes a tracked gap.
4. **Security objectives (Stage 3 / Section 8)** — CIA, privacy, safety, accountability and transparency objectives. Includes the action-authority list: *never* / *only with approval* / *autonomous*.
5. **Threats (Stage 4 / Appendix C, E)** — candidate scenarios generated by rules. The user accepts, edits or dismisses each one, or adds custom scenarios.
6. **Risk & treatment (Stages 5–6 / Section 9–10, Appendix D)** — inherent risk, existing controls, treatment choice (avoid / mitigate / transfer / accept), secure pattern, requirement owner, and residual risk.
7. **Review & export** — completeness checklist (Section 14, scoped to v1), open gaps, then export.

## 3. Domain model (sketch)

- `Assessment`
  - `meta`
  - `intake`
  - `tier`
  - `components[]`
  - `flows[]`
  - `boundaries[]`
  - `answers{}`
  - `objectives`
  - `threats[]`
  - `settings.riskMatrix`
- `Component`
  - `id`, `type`: one of the B1–B17 catalog types (e.g. `vector_store`, `tool_connector`, `model_endpoint`)
  - `name`: the exact name, e.g. "Pinecone prod-kb", not just "vector DB"
  - `owner`, `provider/version`, `environment/region`
  - `classification`, `identity`
  - `plane`: data or control
  - `position`
- `Flow`
  - `source`, `target`, `dataClassification`, `protocol`, `authN`, `authZContext`, `encrypted`
  - `contentOrigin`: one of `user` | `retrieved` | `model` | `tool`
  - `plane`
  - These labels come from Section 7.
- `TrustBoundary`
  - `kind`: one of user↔app, app↔provider, tenant↔tenant, model↔tool, agent↔agent, app↔enterprise, control↔data, public↔private
  - `memberComponentIds`
- `Answer`
  - `questionId`, `targetId`, `status` (Y/N/NA/Unknown), `note`, `evidence`, `owner`, `dueDate`
- `Threat`
  - All the Appendix E fields: ID, location, actor, asset, preconditions, path, impact, controls and evidence, inherent L/I, treatment, pattern, owner, validation, residual.
  - `frameworkTags`: OWASP, ATLAS and STRIDE tags.
  - `sourceRuleId`: the rule that generated it, if any.

## 4. Content libraries (data, not code)

Shipped as versioned JSON/TS data files so they can be edited without touching UI code:

- **Component catalog** — B1–B17 types, each with icon, category, default plane, its questions with a tier per question, and a default secure pattern.
- **Question bank** — Appendix A and B questions, tagged with tier and applicability conditions.
- **Threat rules** — `when` conditions decide when a rule fires.
  - Example conditions: "component of type `tool_connector` with write ops", "flow with `contentOrigin=retrieved` into `prompt_assembly`", "answer B6.Q2 = Yes".
  - Each rule produces a scenario template in the Section 9 narrative format, with framework tags and suggested patterns.
- **Pattern catalog** — Appendix D patterns mapped to threats.
- **Description lexicon** — maps keywords, phrases and product names to suggested components, attributes and answers.
  - Example: "Bedrock" → model_endpoint (provider AWS); "Slack" → tool_connector (messaging); "runs Python" → code_execution.

## 4a. Framework catalogs

Each framework is its own versioned catalog. Each assessment records the catalog versions it was assessed against, so reports stay reproducible after catalogs are updated.

| Framework | Version at spec time | Applies to |
|---|---|---|
| OWASP Top 10 for LLM Applications | 2025 (a 2026 edition could not be confirmed; update the catalog when verified) | GenAI, RAG and agent components |
| OWASP Top 10 for Agentic Applications | 2026 (ASI01–ASI10) | Agents, tools, memory, delegation |
| OWASP Machine Learning Security Top 10 | 2023 (latest) | Traditional ML, training pipeline |
| OWASP Top 10 (web applications) | 2025 (A01–A10) | UI, backend, all app components |
| OWASP API Security Top 10 | 2023 (latest) | APIs, gateways, tool connectors |
| OWASP Non-Human Identities Top 10 | 2025 | Service accounts, agent and tool identities, secrets |
| OWASP Top 10 CI/CD Security Risks | 2022 (latest) | Model and app deployment pipelines |
| OWASP Kubernetes Top 10 | 2022 | Container hosting |
| OWASP ASVS | 5.0 | Verification requirements, mapped to controls and patterns |
| MITRE ATLAS | 2026.10 (verified against official data, Oct 28 2026) | AI-specific tactics and techniques |
| MITRE ATT&CK (Enterprise) | v20.1 (verified against official STIX data), including the v19 split of Defense Evasion into Stealth and Defense Impairment | Conventional attack paths on every component: identity, cloud, network, supply chain, lateral movement |
| STRIDE | n/a | Classifies every threat |

Rules for how the catalogs work:

- **Importable, not hand-typed.** MITRE ATT&CK and ATLAS publish machine-readable data: STIX bundles and the ATLAS YAML/STIX files. Settings → Libraries → *Import framework update* loads a new release.
  - The app shows a diff of added, renamed and deprecated IDs.
  - It flags threat rules whose mapped IDs changed.
  - OWASP lists are maintained as editable JSON catalogs.
- **Every threat gets at least one traditional mapping.** That means a STRIDE category, plus an ATT&CK technique and an OWASP (web, API or NHI) category wherever one applies. AI threats also get their ATLAS and OWASP LLM/Agentic tags.
  - Example: a prompt-injection-to-tool-call scenario is tagged LLM01 + ASI01/ASI02 + an ATLAS technique (LLM Prompt Injection), and also ATT&CK where the resulting action maps (e.g. exfiltration or account manipulation), OWASP A01 Broken Access Control, and STRIDE *Elevation of privilege*.
- **Traditional-only threat rules** exist for every component type (SSRF, IDOR, injection, secrets exposure, misconfiguration, supply chain, lateral movement, logging gaps). AI components are assessed as full applications, not just models.

## 5. Two-way sync rules

- Adding or removing a node on the canvas adds or removes its question set. Answers for a removed node are kept until you confirm deletion.
- Some answers change the diagram. For example, "uses delegated subagents = Yes" offers to add an agent node and a delegation flow.
- Flows that cross a boundary are highlighted. Unlabeled flows and boundaries count toward the completeness score.

## 6. Description → architecture (no-LLM)

1. The user pastes free text.
2. The analyzer tokenizes it and matches it against the lexicon.
3. Results appear as **suggestion cards**, each showing the matched text, the proposed component or answer, and a confidence level.
4. Accepting a card adds it to the model and the diagram. Rejecting a card dismisses it.
5. Nothing is added silently.

## 7. Deferred (post-v1)

- Evidence and control tracker (App. G), test records, and Stage 7 validation.
- Approval and sign-off (App. H), release decision, and reassessment triggers (Section 13).
- LLM-backed description analysis, using a pluggable provider.
- Multi-user collaboration.
- Additional exports: diagram PNG/SVG, CSV/Excel risk register.

## 8. Resolved questions

- Libraries (rules, lexicon, questions, patterns, framework mappings) are editable in-app. Edits are stored locally and can be exported and imported as a library pack (JSON), so they survive browser resets.
- No report branding.
- Frameworks: latest MITRE ATLAS and ATT&CK, and the latest of all relevant OWASP lists, AI and traditional. Traditional security is applied to every component (section 4a).
